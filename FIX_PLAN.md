# План исправлений gorock-kit

Основан на ревью всех модулей. Порядок фаз: сначала то, что ломает прод (зависания, утечки безопасности), потом логика движка, потом компоненты, в конце — ломающие API изменения и релиз.

Принципы:
- Каждый фикс сопровождается тестом, который падает до фикса. Все тесты гоняются с `-race`.
- Одна фаза = один или несколько небольших коммитов по модулю (`[FIX] rockfiber: ...`), чтобы их можно было ревьюить и откатывать по отдельности.
- Тегов ещё нет, проект pre-1.0 — ломающие изменения допустимы, но собраны в отдельную фазу 5 и явно помечены.

## Фаза 1. Критичное: зависания и безопасность

### 1.1 `rocktelebot`: двойной `bot.Stop()` вешает процесс
**Проблема:** `Exec` запускает горутину `<-ctx.Done(); bot.Stop()`, а движок параллельно вызывает `App.Stop()` → второй `tele.Bot.Stop()` навсегда блокируется на `b.stop <- confirm`, т.к. `Start()` уже вышел. Плюс горутина из старого `Exec` переживает рестарт и останавливает уже новый бот.

**Фикс:**
- Убрать горутину из `Exec`. `Exec` запускает `bot.Start()` в горутине и делает `select` на `ctx.Done()` / завершение `Start`.
- Остановка — только через одну функцию `stop()`, защищённую `sync.Once`, который пересоздаётся в `Init` (под мьютексом).
- `stop()` вызывает `bot.Stop()` только если `Start` действительно запущен (флаг `running`, выставляется до старта, снимается после выхода).
- `a.bot` читать/писать под мьютексом.

**Тест:** fake-poller (telebot позволяет передать свой `Poller`, `Offline: true` в `Settings`), сценарии: cancel ctx + `Stop()` одновременно; двойной `Stop()`; `Stop()` до `Exec`; рестарт Stop→Init→Exec→cancel. Все должны завершаться за таймаут теста.

### 1.2 `rockfiber`: pprof доступен без пароля
**Проблема:** `PprofHandler` подключён глобальным `fiber.Use` до группы admin с авторизацией, сам отвечает и не вызывает `Next`.

**Фикс:** перенести pprof внутрь группы admin после `AdminAuthMiddleware`: `admin.Use(AdminAuthMiddleware(...)); admin.Use(pprof.New(pprof.Config{Prefix: adminPath}))`. Добавить флаг `Config.Pprof bool` (по умолчанию выключен) — профилировщик в проде должен включаться осознанно.

**Тест:** `app.Test(httptest.NewRequest("GET", "/admin/debug/pprof/", nil))` → 401 без заголовка, 200 с паролем; 404 при `Pprof: false`.

### 1.3 `rockfiber`: `?debug=` раскрывает внутренние ошибки
**Фикс:** убрать проверку `c.Query("debug")`. Реальное сообщение и так передаётся в `OnError` для логов. Если отладочный режим нужен — `Config.ExposeInternalErrors bool` (только для dev), без управления со стороны клиента.

**Тест:** при заданной маске ответ 500 всегда содержит маску, с `?debug=1` тоже.

### 1.4 Небезопасные значения по умолчанию
- `rockfiber`: CORS по умолчанию — не `*`. Если `CorsConfig == nil`, CORS-middleware не подключается вовсе (браузер сам запретит кросс-доменные запросы), разрешение — явной настройкой.
- ~~`rockbun`: `sslmode` по умолчанию — `prefer`~~ — отменено, см. «Статус».
- Оба изменения поведенческие → отметить в README в разделе «Изменения».

## Фаза 2. `rockengine`: логика жизненного цикла

Все пункты — в `rockengine/engine.go`. Сначала пишется набор тестов с fake-`App` (управляемые каналами Init/Exec/Stop, счётчики вызовов), потом правки.

### 2.1 Нормальная остановка не должна считаться ошибкой
В `runApp` после возврата `Exec` первым делом:
```go
err := ent.app.Exec(ctx)
if ctx.Err() != nil { // остановка по контексту — всегда чистая, что бы ни вернул Exec
    ent.setState(StateStopped)
    return
}
```
`errors.Is(err, context.Canceled)` без отменённого `ctx` — это ошибка приложения, а не остановка, и должна идти через политику рестартов.

### 2.2 Паника в `Exec` подчиняется `RestartPolicy`
Вынести вызов в `safeExec(ctx) (err error)` с `recover` → паника превращается в ошибку (с `debug.Stack()`) и идёт тем же путём, что обычная ошибка. Внешний `recover` в `runApp` убрать.

### 2.3 Сброс счётчика рестартов
Добавить в `RestartPolicy` поле `ResetAfter time.Duration`: если `Exec` проработал дольше — `retries = 0` перед учётом новой ошибки. Значение по умолчанию — 0 (старое поведение, совместимо). В README описать.

### 2.4 Упорядоченная остановка
Сейчас `engineCancel()` отменяет все контексты разом, затем `stopAll` идёт в обратном порядке. Исправить: в `stopAll` для каждого приложения в обратном порядке — `cancel()` его собственного контекста → `Stop()` → `wg.Wait()` этого приложения, затем следующее. Контекст движка отменять в конце. Так HTTP-сервер полностью остановится раньше, чем закроется шина, в которую он публикует.

### 2.5 Таймаут покрывает `Stop()`
Вся процедура остановки (п. 2.4) выполняется в горутине; основной поток ждёт её с `shutdownTimeout`. По истечении — возвращается ошибка с именем приложения, на котором зависли (`shutdown timed out while stopping "bot"`). Для этого текущее останавливаемое имя хранится в atomic-переменной.

### 2.6 `recover` во всех вызовах `Init`/`Stop`
`safeInit` использовать также в `doRestart` и `RestartApp`; добавить `safeStop` для всех вызовов `Stop`. Паника в пользовательском коде не должна ронять движок.

### 2.7 Опция «фатальная ошибка останавливает движок»
`Engine.WithStopOnFatal(true)` (и `rockengine.SetStopOnFatal`): при переходе любого приложения в `StateFailed` вызывается `engineCancel()`, `RunContext` возвращает ошибку с именем приложения и причиной. По умолчанию — **включено** (решение: живой процесс с мёртвым компонентом хуже, чем перезапуск контейнера оркестратором). Это изменение поведения → отметить в README.

### 2.8 Мелочи
- Приложение в `StateFailed` сразу получает `Stop()` (освобождение ресурсов), а не только при общей остановке.
- `RestartApp` во время остановки движка — проверять флаг `stopping` под мьютексом, а не только `engineCtx.Err()`.

**Тесты фазы 2** (таблицей): clean exit; exit с ошибкой при `MaxRetries` 0/N/-1; `RestartOnExit`; паника в Init/Exec/Stop; Exec возвращает произвольную ошибку после cancel → `Stopped`, без `OnFatal`; порядок вызовов Stop (проверяется записью в общий слайс); зависший Stop → возврат по таймауту с именем; `StopOnFatal`; `ResetAfter`; `RestartApp`/`StopApp` при работающем и остановленном движке.

## Фаза 3. Компоненты

### 3.1 `rockfiber`: рестарт
- В `Init` пересоздавать `stopOnce` (хранить `*sync.Once` и заменять под мьютексом) и `a.fiber`; доступ к `a.fiber` — под мьютексом.
- Тест: Init→Exec→Stop→Init→Exec→cancel; проверить, что порт освобождён (повторный `net.Listen` на тот же порт успешен).
- Решить судьбу `SetEndpoints`: вернуть эндпоинты в `New(cfg, endpoints ...FiberEndpoint)` (как в README) и оставить `SetEndpoints` как дополнительный путь; ошибку «SetEndpoints must be called» убрать — сервер без пользовательских маршрутов (только `/status`) допустим.

### 3.2 `rockbus`
- **Потеря события при остановке:** заменить пару «канал `done` + select» на счётчик/мьютекс публикаций: `PublishAsync` берёт `RLock` на `stateMu`, проверяет `stopped`, кладёт в канал (неблокирующе) и отпускает; `Stop` берёт `Lock`, ставит `stopped = true`, закрывает очереди. После `Lock` новых записей в каналы гарантированно нет, воркеры дочитывают канал через `range` до закрытия. Событие либо обработано, либо ушло в `OnError` — третьего не дано.
- **Гонка `stopOnce`:** при новой схеме `stopOnce` не нужен — состояние под мьютексом.
- `Subscribe` на новый топик после `Exec` — возвращать ошибку (или паниковать с понятным текстом) сразу, а не молча ждать `ErrNoWorker` при публикации. Сигнатура `Subscribe(...) error` — ломающее изменение → фаза 5, пока — документировать.
- В README явно написать: доставка in-memory, at-most-once, при падении процесса события теряются; медленный обработчик блокирует свой топик.
- Тесты: конкурентные `PublishAsync` во время `Stop` (1000 горутин) — сумма «обработано + OnError» равна числу публикаций; рестарт; переполнение очереди.

### 3.3 `rockcron`
- Разбор таймзоны и регистрацию расписаний перенести в `Init` (создавать `*cron.Cron` там) → ошибки конфигурации падают на старте, а не крутят рестарты.
- Та же схема состояния под мьютексом вместо `stopOnce` (гонка).
- Исправить комментарий `Stop()` или сделать, чтобы он действительно ждал (`<-c.Stop().Done()` в `Stop` с учётом, что `Exec` тоже ждёт — вызывать один раз).
- Задачам передавать контекст, отменяемый и при `Stop()`, а не только при отмене ctx `Exec`.
- Тесты: невалидное выражение → ошибка из `Init`; `@every 10ms` выполняется; Stop ждёт выполняющуюся задачу; паника в задаче → `OnError`.

### 3.4 `rockbun` / `rockredis`
- Если `Ping` в `Init` не прошёл — закрыть только что созданный пул и вернуть ошибку; при повторном `Init` закрывать предыдущий.
- `rockbun.buildDSN` — собирать через `url.URL{Scheme: "postgres", User: url.UserPassword(u, p), Host: ..., Path: db, RawQuery: ...}`.
- Тесты: `buildDSN` с паролем `p@ss:/#w`; утечка пула — через `testcontainers` или пропуск, если нет `DOCKER_HOST` (интеграционные тесты под build-тегом `integration`).

### 3.5 `rocklog`
- `Fatal`: оставить, но в документации явно предупредить, что он обходит graceful shutdown движка; в примерах заменить на `Error` + возврат ошибки.
- Контекстное логирование: `rocklog.WithContext(ctx, fields...) context.Context` и `rocklog.FromContext(ctx) Logger`. В `rockfiber` trace-id кладётся в `UserContext` (не только в `Locals`), чтобы логгер мог его достать.
- Переход на `slog` — см. фазу 5.

| 4.7 | Переполнения | Проверять `field.OverflowInt/OverflowUint/OverflowFloat`; отрицательный int в uint — ошибка. |

Тесты — таблицей для каждого пункта: YAML и JSON вход, ожидаемая структура или текст ошибки. Это самый удобный для покрытия модуль, начать тестирование можно с него.

API: `InitFromFile[C](path string, opts ...Option)` — добавление вариативного параметра обратно совместимо.

## Фаза 5. Ломающие изменения API (требуют решения)

Каждый пункт — отдельное решение. Мои рекомендации:

1. **`Stop` с контекстом: `Stop(ctx context.Context) []error`** — дедлайн остановки передаётся явно, компонентам не нужны собственные `ShutdownTimeout`. Рекомендую: **да**, это главный источник ошибок, найденных в ревью. Затрагивает все lifecycle-модули и движок, делается одним коммитом.
2. **Единый контракт для `rockbun`/`rockredis`**: либо они реализуют `App` (с `Exec`, который просто ждёт `ctx.Done()`), либо движок получает отдельный тип «ресурс» (`Init`/`Close`), регистрируемый тем же `Register` и закрываемый после всех приложений. Рекомендую: **ресурс** — `Exec` у пула соединений искусственный.
3. **`rocklog` на `slog`**: интерфейс `Logger` сохранить, бэкенд — `log/slog` (меньше зависимостей, быстрее); logrus-бэкенд — опционально. Рекомендую: **да**, совместимо на уровне API `rocklog`.
4. **`rockbus.Subscribe` возвращает `error`** (см. 3.2). Рекомендую: да.
5. **`rockredis`**: оставить узкий `Service` для тестируемости, но добавить `Client() *redis.Client` для всего, чего в обёртке нет, и не расширять интерфейс дальше. Рекомендую: да.
